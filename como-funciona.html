Mercury · Software Factory Template

Mercury: una fábrica de software que codea sola y deja las decisiones importantes a las personas

Este repo define un agente orquestador (Mercury) construido sobre el framework eve. Toma issues de GitHub o Linear, los pasa por cuatro estaciones especializadas de IA, y entrega un draft pull request revisado. Nadie mergea sin que una persona lo apruebe.

agent/agent.ts agent/instructions.ts agent/subagents/* Vercel · GitHub · Linear · Blob
el trabajo fluye de las fuentes → Mercury → las cuatro estaciones → un pull request en draft

Qué es

Un orquestador, cuatro estaciones, un solo entregable

Mercury nunca escribe código ni analiza a fondo por su cuenta: enruta trabajo, verifica lo que cada estación devuelve, y arma el resultado final. Cada estación es un subagente declarado con sus propias instrucciones, su propio sandbox (un checkout del repo) y su propio conjunto de herramientas. eve descubre todo esto directamente del sistema de archivos bajo agent/: no hay un registro central ni un archivo de "wiring".

Descubrimiento por filesystem

El nombre de una tool es su nombre de archivo; el de un subagente, su carpeta; el namespace de una extensión, su archivo. No hay configuración manual de rutas.

Estaciones aisladas

Un subagente corre en una sesión hija fresca y no hereda nada del root: ni instrucciones, ni skills, ni conexiones, ni sandbox. El orquestador empaqueta todo en el mensaje.

Personas en el loop

El resultado siempre es un PR en draft. Marcarlo "ready" y mergear son decisiones humanas; mergear ni siquiera está en el set de herramientas del agente.

El corazón del sistema

El pipeline: classifier → analyst → implementer → reviewer

Las estaciones corren siempre en este orden, sin excepciones ("trivial" lo decide el classifier, no el orquestador). Cada mensaje de delegación es autocontenido: las estaciones no ven el historial de conversación del root, así que reciben el work item completo más todo lo que salió de las estaciones anteriores.

🧠
La "factory brain" no es una estación, es memoria compartida.

Notas durables sobre el repo objetivo (mañas del build, pasos de verificación no obvios, hallazgos de review recurrentes, convenciones) guardadas en Vercel Blob. Mercury la lee al empezar cada tarea y, como las estaciones no pueden leerla directamente, teje los datos relevantes en los mensajes que les manda. Al terminar, si aprendió algo durable, la actualiza. Las lecturas están abiertas a cualquier corrida; la escritura está protegida (más abajo).

Disparadores

Cómo llega el trabajo

Cinco formas de arrancar una corrida, cada una con su propio nivel de confianza y de autonomía.

Label factory

No supervisado. Un mantenedor etiqueta un issue. La sesión corre bajo un principal autónomo construido para la ocasión: puede postear comentarios de progreso, etiquetar, cerrar/reabrir el issue de origen y abrir PRs en draft, pero nada más. Si necesita aclaración, pregunta y se detiene (nunca deja una corrida no supervisada esperando input).

@Mercury mention

Supervisado. Solo owners, members y collaborators del repo pueden invocarlo comentando en un issue o PR; cualquier otro es ignorado. La sesión corre con esa persona del otro lado: las preguntas van a ella y las acciones que "envían" algo (ready, etc.) esperan su aprobación.

Linear Agent Sessions

Alguien delega un issue en Linear. La sesión queda marcada de confianza (la membresía al workspace ya es el filtro), reporta progreso como Agent Activities y al final devuelve el link del PR en la misma sesión.

TUI local (pnpm dev)

Se le pasa un work item a mano. El principal de dev es deliberadamente no confiable, así que cualquier escritura en GitHub queda en pausa esperando una aprobación en la propia TUI: es, de hecho, una demo en vivo del gate humano.

CI en rojo sobre un PR factory/*

Un check_suite fallido sobre un PR que la propia fábrica empujó dispara una corrida no supervisada: diagnostica la falla y empuja un fix a la misma rama. Cuenta los intentos previos en los comentarios del PR y, tras 2 intentos sin éxito, se detiene y pide una persona. Los PRs que empujó una persona nunca se tocan.

De punta a punta

El recorrido completo de un work item

1. Se agarra el trabajo real

Antes de rutear nada, Mercury lee el issue/PR/issue de Linear real (nunca inventa números, títulos o estados) y aplica la skill triaging-issues: busca duplicados, aprende el vocabulario de labels del propio repo y decide si preguntar o avanzar.

2. Corre el pipeline en orden

classifier → (researcher opcional, si falta un dato externo verificable) → analyst → implementer → reviewer. Cada delegación es un mensaje autocontenido; ninguna estación ve el historial del orquestador.

3. Si el reviewer aprueba

Se abre un PR en draft con github__createPullRequest, contra la rama por default del repo. El cuerpo se arma con el problema, el enfoque, los criterios de aceptación marcados pasa/no pasa, comandos de verificación y sus resultados, y "Closes #N" si aplica.

4. Se reporta y se guarda memoria

Mercury contesta en el hilo de origen con el link del PR y un resumen. Si aprendió algo durable sobre el repo (una maña del build, un hallazgo de review recurrente), lo agrega a la factory brain.

5. Una persona decide el resto

Marcar el PR "ready for review" y mergear son pasos humanos. Mergear ni siquiera está en el set de tools del agente.

El modelo de confianza

Qué puede hacer cada tipo de llamador

La confianza se decide en el dispatch (en los hooks de los channels), nunca en el prompt. Todo vive en agent/lib/trust.ts y las políticas de aprobación de agent/lib/github/approval.ts: cada tool de escritura de GitHub devuelve not-applicable (corre), user-approval (espera a una persona) o denied según quién llama.

Barreras estructurales, no promesas del prompt

Seguridad y aislamiento

Las garantías importantes están en el código, no en instrucciones que el modelo podría ignorar.

🔒 Las credenciales de git nunca entran al sandbox

Los clones, fetches y pushes de las estaciones apuntan siempre a https://github.com/<FACTORY_REPO>.git literal, nunca al remoto origin (que el modelo podría reescribir). El token de instalación se inyecta a nivel del firewall del sandbox, como transformación de headers al salir hacia github.com, y se descarta después.

🔒 push_branch es inofensivo por construcción

validateBranch rechaza main/master, refs/*, HEAD y cualquier carácter fuera de un set conservador (para que ningún metacarácter de shell llegue a la línea de comandos). Una rama feature sola no puede shippear nada.

🔒 Las estaciones corren en "task mode"

Cada agent.ts de estación declara un outputSchema: eso obliga a devolver salida estructurada y les impide pedir aprobaciones o esperar input. Por diseño, ninguna herramienta dentro de una estación puede necesitar aprobación humana.

🔒 El label factory no se puede falsificar

Solo la acción labeled del webhook dispara la corrida; un label puesto al crear el issue (que los templates permiten a reporters no autenticados) no cuenta. Aplicar un label requiere permiso de triage sobre el repo.

ℹ️ Draft PRs son el techo de lo no supervisado

Cualquier PR con draft: true corre para cualquier llamador porque un draft no puede mergearse. Todo lo que sí puede shippear (PRs no-draft, marcar ready) espera a una persona y está denegado sin supervisión. Las tools de merge ni siquiera están en el set de herramientas.

ℹ️ Superficie de prompt-injection

La fábrica lee cuerpos de issues, comentarios y diffs de terceros, y sus estaciones ejecutan código del propio repo (tests, lint) dentro de sandboxes. El límite es estructural: sesiones no supervisadas corren bajo el principal autónomo denegado por defecto, la conexión de Linear niega escrituras sin supervisión, y todo lo que shippea necesita una persona.
